# 移植类改动的操作说明

以“把新机型上的某个成像风格移植到旧机型”为例，说明这类改动如何分层、按什么顺序执行、每步如何验证与回滚。

本文只讲方法、顺序与判据；偏移与写入字节数集中在 [FL2/FL3 落点与验收细节](FL23_DETAILS_2026-10-25.md)，那一篇给数字、不含哈希。

---

## 1. 先判断：是缺能力，还是缺接入

目标往往不是“让旧机型跑一段新代码”，而是“旧机型的处理链已具备执行能力，只是缺少把某个模式接进链路的最后一环”。

所以判断顺序应当是：

1. 能力是否已存在于固件中（处理链、参数表、数据结构）；
2. 若已存在，缺的是开关、映射关系，还是数据本身；
3. 只在确认缺失项之后，才讨论是否需要改动固件文件。

跳过前两步直接“改哪里”，会放大风险，也容易把现象误判为能力缺失。

### 1.1 三条独立证据，缺一不可

| 证据 | 要回答的问题 | 典型反例 |
|---|---|---|
| 符号/参数 | 处理链里有没有这项能力的名字与参数 | 只有接口枚举，没有参数声明 |
| 参数链 | 读取、判定、写入、生效是否首尾相接 | 能写入但不广播、不重算 |
| 准入层 | 菜单权限、机型能力表、可用性计数是否放行 | 代码在，能力表里没有这一项 |

三条都齐，才叫“只差接入”；只有第一条，通常只是“平台里编进了这个词”。

### 1.2 同代平台不等于同机型

同一代平台上，图像引擎、色彩模块、菜单框架往往是共享的，差异主要落在**机型能力表**（哪些能力允许被这台机器表达）与**产品配置数据**（默认值、可用性计数、菜单权限列）。因此“代码都在、菜单没有”通常不是引擎缺失，而是准入层没放行；反过来，能力表里连这个词都没有时，改菜单也不会生效。

---

## 2. 改动分成哪几层

这类移植通常落在三个互相独立的位置，必须分开做、分开验证：

| 层 | 位置 | 作用 |
|---|---|---|
| A. 应用层映射 | 应用主程序 | 把“用户选的选项”翻译成内部的成像模式编号 |
| B. 成像处理数据 | 协处理器侧的模式数据文件 | 提供该模式实际使用的参数集合 |
| C. 色彩参数单元 | 独立的参数存储单元 | 存放该风格的色彩/伽马参数 |

三层的性质差别很大：A 层是启动关键路径上的一小段代码；B 层是“原地替换若干区间”的较大数据文件；C 层只写设置数据，不碰任何固件镜像。

### 2.1 三层各自的注意点

- **A 层**常同时涉及转换逻辑（外部选择 → 内部模式编号）、能力表/权限列（选项是否可见）、可用性计数（多份引用共同决定可用/不可用）。只改逻辑会“生效但菜单不出现”，只改准入层会“菜单出现但选不中”。
- **B 层**通常有两份数据：可选择的模式表（能不能切过去）与当前生效的模式数据（切过去用什么参数）。两份不一致会出现“显示已切换、成像没变”或“刚切有效、冷启动后回退”。
- **加载时机不同**：C 层通常下次启动生效；B 层必须完整断电冷启动；A 层在进程启动时加载。这是“看起来改了却没生效”的最常见来源。

---

## 3. 前置条件（缺一不可）

- 电量充足，并准备备用电池；任何写入过程都不要碰线、不要断电；
- 准备好**官方恢复包**（对应机型的官方固件更新文件），这是唯一的救生索；
- 先做**只读预检**：确认目标分区可写、当前固件为用户预期的版本；
- 先做**完整备份**：至少有一份改动前的原始数据副本，回滚不依赖相机上的残留状态。

另外三点：恢复包要先验证可用（版本匹配、介质可读、升级入口能进）；备份要离线保存；每次写入前重新比对版本指纹，防止在错误版本上操作。

---

## 4. 执行顺序

顺序的原则是：**先做最容易恢复的，最后做最难恢复的。**

```
1. C 层：色彩参数单元    —— 只写设置数据，可逆，风险最低
2. B 层：CP 模式数据      —— 原地替换区间，有明确的前后状态判定
3. A 层：应用层映射       —— 最后做，改动最小但后果最重
```

每一层做完都要单独验证，确认无误后再进入下一层。不要三层连着做——一旦成像不对，无法判断是哪一层。层与层之间留一个“回到已知良好状态”的检查点：任何一层失败，先回滚该层，不要带着问题继续。

---

## 5. 每层怎么验证

**C 层**：写入前后各读一次单元内容，比对差异是否只在预期区间内；写入后读回校验。

**B 层**：改动前记录原文件指纹，改动后读回并比对。注意这一层的数据**必须断电冷启动才会生效**，热重启读到的仍是旧内容，不要据此判断失败。

**A 层**：写入前比对整文件指纹是否为预期的原始版本，写入后读回校验；随后做**冷启动验证**——清掉所有运行时补丁、完整断电、重新开机，确认结果来自文件本身而不是内存补丁。

**成像验证**：固定机位、固定曝光参数，拍摄一组对照照片，用可量化的方式比较，而不是只看观感。

### 5.1 验收记录

| 项目 | 记录内容 |
|---|---|
| 版本 | 改动前的整文件/整单元指纹 |
| 窗口 | 实际改动的区间与改动前后内容 |
| 读回 | 写入后立即读回的结果 |
| 冷启动 | 完整断电后的状态 |
| 功能 | 目标模式是否可选、是否实际生效 |
| 菜单 | 名称/图标是否变化（与功能分开记） |
| 回滚 | 是否演练过、回滚后指纹是否复原 |

成像对照要同镜头、同机位、同曝光与白平衡，覆盖高光、阴影、肤色与高饱和色；“观感更好”不是验收标准。

### 5.2 数据规模（以一次 FL2/FL3 移植为例）

三层的数据量级差别很大，先按规模判断“这一步值不值得做”：

| 层 | 载体 | 载体大小 | 实际改动量 | 生效条件 |
|---|---|---:|---:|---|
| A 应用层映射 | 应用主程序 | 89,027,992 B | 112 B 窗口（一条转换分支） | 冷启动 |
| B 成像处理数据 | CP 模式数据文件 | 17,892,024 B | 9,536 B delta / 33 个窗口，实际写入 4,456 B | 完整断电 |
| C 色彩参数单元 | 两个参数单元 | 8,192 B + 28,672 B | 71 B + 840 B = 911 B，落到两个空槽 | 下次启动 |

几个读法：

- A 层只改一个 112 B 的转换窗口，但窗口前后都要做**整文件**指纹校验，不能只看窗口；
- B 层是 33 个窗口的 delta，每个窗口写前校验 before、写后回读 after，任何一个不匹配就整批中止；
- C 层虽然只动 911 B，但目标槽必须是空的且没有被其他参数引用，否则会出现“改了 A 槽、B 槽却还在用旧数据”；
- 三层的载体大小与实际改动量相差几个数量级，所以“改动小”不等于“风险小”，风险由所在层决定。

### 5.3 一次完整验收的口径（示例）

| 阶段 | 数量 | 通过标准 |
|---|---:|---|
| 离线分支验证 | 525 组 × 3 轮 | 只有目标分支变化，其余输入输出逐字节一致 |
| 独立实现交叉核对 | 19 项 | 双方地址/结果一致，不一致项要能解释 |
| 实机成像对照 | 6 张 | 固定机位、同曝光/白平衡，RAW+JPEG 各一组 |
| 冷启动 | ≥ 3 次 | 每次都能复现，且不依赖运行时补丁 |
| 回滚演练 | 每层 1 次 | 回滚后整文件/整单元指纹回到改动前 |

配套的“失败但正常”清单，避免把预期行为当成故障：

- 菜单文字/图标不变：正常，成像链与资源管线是两套；
- B 层热重启不生效：正常，必须完整断电；
- 第一次冷启动后模式仍在，但第二次启动消失：多半是两份模式数据不一致，不是写入失败。

### 5.4 结构规模

除了“改了多少字节”，还要知道“这些字节落在什么结构里”，否则无法判断改动是否完整：

| 结构 | 规模 | 与本次移植的关系 |
|---|---:|---|
| 风格枚举 | 每族 16 槽（旧机型） | 目标风格只能落到空槽，槽位不能复用 |
| 内建风格 | 10 个 | 自定义槽的图标最多只能引用这 10 个之一 |
| look 记录 | 每条 160 B | 名称、引导语、图标槽、参数索引都在一条记录里 |
| CP 候选模式 | 42 项 | 实际只启用其中两项，其余保持原值 |
| 模式数据窗口 | 33 个 | 每个窗口独立校验，缺一个都不算完成 |
| 色彩参数 | 每槽 8 项 | 对比度、高光、阴影、褪色、饱和度、锐度、范围、清晰度 |

两个容易忽略的点：

- **槽位是稀缺资源**：空槽被占用后，后续再移植别的风格就没有位置了，规划时要一次留够；
- **参数是整组生效**：8 项里改错一项，成像就会偏，不能只对单项做“看起来差不多”的判断。

### 5.5 为什么位置不写在这一篇里

本文只讲分层方法与验收判据；偏移、窗口长度与写入字节数集中在 [FL2/FL3 落点与验收细节](FL23_DETAILS_2026-10-25.md)。位置只放一处、并在那一处写明适用版本，是为了避免它被当成通用教程照抄；那一篇同样不含哈希。

112 B 很小，但它位于启动关键路径的一个转换函数里。写错的后果是主程序无法启动、运行时通道同时失效，只能靠官方恢复包，所以位置必须和版本前提绑在一起看。

确认自己找到的是不是那一处，仍然靠行为验证更可靠：固定一组输入跑一遍，只有目标两项变成新值，其余逐字节不变。

---

## 6. 回滚

- **C 层**：直接用备份的单元内容回写；
- **B 层**：用备份的数据文件整段回写，回滚后同样需要断电冷启动；
- **A 层**：用备份复回原始代码；若写入损坏导致主程序无法启动，只能靠官方恢复包。

回滚过程不应依赖被改动的那部分功能——这一点在设计阶段就要确认。回滚顺序与写入顺序相反（先 A、再 B、后 C），前提是主程序还能启动；回滚后要完整断电冷启动，并重新计算整文件指纹，确认与改动前一致，而不是只看某个窗口。

---

## 7. 已知的坑

1. **只切电源开关不够**：必须完整断电（拔电池），否则新数据不会加载，旧状态还留在运行期；
2. **B 层的改动热重启不生效**，容易误判为失败；
3. **运行时补丁会掩盖文件改动**：验证文件层时必须先清掉所有内存补丁，否则测不出真实结果；
4. **界面不一定会变**：成像参数已经生效，但菜单里的名字/图标可能仍是旧的，这不代表改动失败；
5. **不同固件版本结论不同**：同一机型的不同固件版本，内部结构可能有差异，不要跨版本照搬；
6. **两份模式数据不一致**：会出现“能选但不生效”或“生效后回退”；
7. **AP 与 CP 各自独立回滚**：两边版本会漂移，必须分别记录状态；
8. **只比对首字节不够**：写入窗口要整段读回校验，局部位翻转可能不改变首字节。

---

## 8. 为什么菜单文字/图标通常不能一起移植

成像、文字、图标是三条不同的管线：成像链是“模式编号 → 参数集合 → 色彩/伽马”；文字来自应用资源里的字符串表，旧机型可能根本没有目标字符串；图标走资源 id 与图库，图标槽位与成像模式并不一一对应。

所以“功能生效”与“菜单改名”要分开立项、分开验收。多数情况下，正确做法是接受旧名字、只保证功能与参数正确；强行改文字/图标要动资源打包与引用表，收益低、风险高。

---

## 9. 风险对照

| 层 | 写坏后的后果 | 恢复手段 |
|---|---|---|
| C 层 色彩单元 | 成像异常，菜单可能报错 | 回写备份即可 |
| B 层 模式数据 | 成像异常或无法启动 | 回写备份；必要时官方恢复包 |
| A 层 应用层映射 | 主程序无法启动，运行时通道同时失效 | 仅官方恢复包 |
| D. 运行时补丁 | 本次开机内异常，断电即消失 | 断电重启；不要与文件改动混用 |

因此 A 层永远放在最后，且必须在 B、C 两层都验证通过、且已确认恢复包可用之后才动。运行时补丁只适合验证行为，不适合作为最终形态；验证文件层之前必须先清掉它。

---

## 10. 常见误判

- **把“界面没有变化”当作“功能没有生效”**：界面与功能往往是两套机制，功能可能已生效而界面没有消费者；
- **把“选项可选”当作“链路打通”**：可选只说明准入判断通过，不代表下游的联动（参数重算、状态广播）已经发生；
- **把“数据存在”当作“数据正确”**：表项存在与表项内容符合预期是两件事；
- **把“热重启后还在”当作“已持久化”**：有些状态来自运行期缓存，只有完整断电才能区分。
