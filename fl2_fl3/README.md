# 移植类改动的思路拆解

以一个“把新机型上的某个成像风格移植到旧机型”的设想为例，说明这类改动应该如何拆解、验证与回退。文中不涉及具体字节、偏移或数据格式。

## 问题形态

目标不是“让旧机型跑一段新代码”，而是“旧机型的处理链其实已经具备执行能力，只是缺少把某个模式接进链路的最后一环”。

因此判断顺序应当是：

1. 能力是否已存在于固件中（处理链、参数表、数据结构）；
2. 若已存在，缺的是开关、映射关系，还是数据本身；
3. 只在确认缺失项之后，才讨论是否需要改动固件文件。

多数时候社区容易跳过第 1、2 步，直接进入“改哪里”，这会放大风险，也容易把现象误判为能力缺失。

## 分层的必要性

这类改动天然跨越多个独立层次，例如：

- 应用层的“选项到内部模式”的映射；
- 运行在另一颗处理器上的处理程序（其对模式的接受度可能与直觉不同）；
- 存放成像参数的数据单元。

这三层可以独立验证、独立回滚。把它们混在一起做一次性写入，是主要的风险来源：一旦成像不对，无法判断是哪一层的问题。

## 验证方法

原则只有一条：**先用不持久的改动验证行为，确认正确后才考虑持久化**。

- 不持久的改动发生在运行时内存中，断电即消失，且不影响固件文件；
- 持久化写入是最危险的一步，一旦写坏，设备可能无法启动，且运行时通道同时失效；
- 因此持久化应当放在最后，并且必须预先准备好官方恢复手段。

## 常见误判

- **把“界面没有变化”当作“功能没有生效”**：界面与功能往往是两套机制，功能可能已生效而界面没有消费者。
- **把“选项可选”当作“链路打通”**：可选只说明准入判断通过，不代表下游的联动（参数重算、状态广播）已经发生。
- **把“数据存在”当作“数据正确”**：表项存在与表项内容符合预期是两件事。

## 回退思路

任何一层改动都应当能够在不依赖设备状态残留的前提下回到初始状态：

- 运行时改动：断电即可；
- 持久化改动：需要保留原始数据的完整副本，且恢复过程不应依赖被改动的那部分功能。

## 结论

这类工作的价值主要在于**把“能不能”分解成可验证的子问题**，而不是尽快写进去。分得越细，出错时的定位成本越低，回退也越简单。
